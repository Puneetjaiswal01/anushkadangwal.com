# Activate private study spaces

This branch prepares authenticated private progress. It is **not active on the production website** until the hosting settings below are configured, checked, and the branch is deployed. The current production guest links still allow profile switching.

## Permissions

| Signed-in person | Can read | Can update |
| --- | --- | --- |
| Anushka | Anushka, Hardik, Ojasvi | Anushka |
| Hardik | Hardik | Hardik |
| Ojasvi | Ojasvi | Ojasvi |

Anushka sees partner spaces read-only. A profile query parameter chooses a view, never an identity. The server independently checks every data request. A guest cannot gain access by editing a URL, a role field, a backup, or a browser button.

## Required hosting configuration

Set these **private Vercel environment variables**, not public frontend variables:

- `CAT_PASSWORD_HASHES`: JSON records for the three passwords, generated by the helper below.
- `CAT_SESSION_SECRET`: a random server signing secret, also generated by that helper.
- `CAT_REDIS_REST_URL`: HTTPS URL of a private Upstash-compatible Redis REST database.
- `CAT_REDIS_REST_TOKEN`: that database’s private REST token.

An existing compatible private database can be reused. No database account, credentials, pricing choice or storage resource was assumed or provisioned. Keep preview and production data separate. The cloud environment’s pending `VERCEL_TOKEN` requirement has no saved binding; supplying it securely would allow the agent to configure/verify the Vercel project. It does not itself create a database or choose the users’ passwords.

Do not paste passwords or tokens into chat or commit them to Git. To create the password configuration in your own terminal:

```sh
node scripts/create-access-config.cjs /private/path/cat-access.private.json
```

The helper asks for each password twice, requires at least 12 characters, does not echo passwords, and writes only password hashes plus a generated session secret into a new file with owner-only permissions. Add those values securely to Vercel settings and keep the file private. Each person signs in with `anushka`, `hardik`, or `ojasvi` and their password.

## Data migration

After configuration and deployment, Anushka should sign in first on any browser containing earlier guest records. Existing browser records are transferred to empty private records before the old plaintext copies are removed. Earlier test drafts are included. The shared migration endpoint is owner-only and refuses to replace an existing private record. A guest whose browser contains only their own earlier profile can transfer that record through the normal own-account API; they cannot export or clear another person’s earlier record.

If private progress already exists, the UI stops and preserves the remaining browser copies for manual review/export. It never silently merges conflicting notes or discards one version. Guest access on that browser stays blocked until Anushka resolves those old shared copies. Already-present plaintext cannot be retroactively protected before that migration.

After transfer, normal progress and test drafts are kept in the private store, not shared localStorage/sessionStorage profile keys. Export/restore remains available within the matching account. Version conflicts preserve the pending work and require review rather than overwriting newer data.

## Deployment and checks

The build uses only Node.js built-ins; no runtime npm dependencies are required. `npm run build` copies only public learning files to `public/`; server code and private configuration are excluded. Vercel serves `api/access.js`, `api/progress.js`, and `api/migrate.js` as Node functions.

The application deliberately fails closed without its private settings. Do not merge/deploy it to production and describe access as ready before configuration and real datastore verification. A preview without settings displays a setup-pending sign-in screen.

Local checks use isolated, temporary test credentials and an in-memory test datastore, never production accounts:

```sh
npm run build
npm run test:access
npm run test:browser
```

API tests cover authentication, per-person permissions, read-only owner inspection, forged cookies/roles, cross-origin requests, stale writes, logout revocation, rate limits, validation and public-file exclusions. Browser tests cover real sign-in, own-space redirects, forbidden direct API access, private persistence, owner inspection, old-data migration, logout, missing-configuration lockout, and the existing learning tools.

Production verification still needs the real private environment values and a persistent datastore. It has not been claimed from fixture tests.
